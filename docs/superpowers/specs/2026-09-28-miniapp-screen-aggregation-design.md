# 微信小程序 84 页真实数据聚合层设计

## 1. 背景与目标

当前 S01-S84 已完成页面注册和基础导航，但页面数据存在两套来源：

- 部分页面在 `BlueprintScreen` 中逐页调用领域接口。
- 未接入接口或请求失败的页面继续展示 `src/data/fixtures.ts` 的静态内容。

这种结构会造成重复请求、页面分支持续膨胀，并可能把示例金额、状态和数量误认为真实业务结果。

本次改造采用已确认的方案 A：保留项目、任务、财务、证据等现有领域写接口，新增只读的小程序页面数据聚合层。最终目标是 S01-S84 全部只展示当前用户在当前租户和当前业务上下文中可访问的真实数据；无数据展示真实空状态，请求失败展示明确错误，不再回退到示例数据。

## 2. 设计原则

1. 聚合接口只负责查询和展示模型组装，不承载领域写操作。
2. 金额、比例、状态和数量均从数据库记录或既有计算函数得出，不在客户端硬编码。
3. 缺失值保持缺失，不按零补齐，不生成推测性业务结果。
4. 所有项目级查询必须同时校验当前租户和项目归属。
5. 页面定义、数据提供器和前端路由形成显式映射，S01-S84 不允许隐式默认提供器。
6. 搜索结果保存真实实体 ID；显示文本只用于呈现，不能作为后续写操作的主键。
7. 现有未提交功能改动继续保留，聚合层在其上增量实现。

## 3. API 契约

新增接口：

```http
GET /miniapp/screens/{screen_id}?project_id=&version_id=&task_id=&artist_id=&keyword=
```

`screen_id` 仅允许 `S01` 至 `S84`。查询参数按页面需要选填；缺少必需上下文时返回可识别的业务错误，不使用默认项目 ID。

统一响应继续使用现有包装：

```json
{
  "code": 0,
  "data": {
    "screen_id": "S10",
    "summary": {
      "title": "我的项目",
      "subtitle": "快速查看判断、待办和版本变化",
      "highlight": "2 个进行中"
    },
    "items": [],
    "options": {},
    "context": {
      "tenant_id": 1,
      "project_id": null,
      "version_id": null,
      "task_id": null
    },
    "empty_state": {
      "title": "暂无项目",
      "description": "创建项目后可在这里查看判断与待办",
      "action": {
        "label": "创建项目",
        "target_screen": "S13"
      }
    }
  },
  "message": "ok"
}
```

字段语义：

- `summary`: 页面级标题、说明和由真实数据计算的关键指标。没有可靠指标时 `highlight` 为 `null`。
- `items`: 当前页面的主要列表或详情条目。每项包含稳定 `id`、`entity_type`、`title`、可选描述、状态、数值及导航上下文。
- `options`: 表单选项、筛选条件、权限开关或图表序列。只返回页面实际需要的数据。
- `context`: 服务端确认后的租户、项目、版本、任务和艺人上下文。
- `empty_state`: `items` 为空时的真实空状态。非空时为 `null`。

错误语义：

- `400`: screen ID 或查询参数无效。
- `401`: 登录上下文失效。
- `403`: 当前用户无权访问租户、项目或实体。
- `404`: 必需的项目、版本、任务或实体不存在。
- `409`: 客户端版本上下文落后，需要重新加载。
- `422`: 页面所需业务参数缺失，例如财务页面缺少真实成本参数。
- `5xx`: 服务异常。客户端显示错误和重试入口，不保留旧示例内容。

## 4. 后端架构

### 4.1 路由与服务边界

- `app/routes.py` 仅解析请求、获取用户上下文并返回 `json_ok`。
- 新增 `app/miniapp_screens.py`，包含 screen 注册表、上下文校验和聚合服务。
- 每个提供器接受统一的 `ScreenContext`，返回统一的 `MiniappScreenData`。
- 同一领域的多个页面复用查询函数，例如 S10/S11/S12 共享项目查询，S25-S33 共享财务快照解析。
- 聚合器直接复用现有财务计算和序列化函数，不通过 HTTP 回调本服务自身。

建议的注册形式：

```python
SCREEN_PROVIDERS = {
    "S10": project_list_screen,
    "S11": project_detail_screen,
    "S25": finance_input_screen,
}
```

注册表必须完整覆盖 S01-S84。不存在默认提供器，避免新增页面静默落入错误数据源。

### 4.2 查询与权限

聚合请求从认证信息和 `X-Tenant-Id` 建立当前上下文。项目、版本、任务、事实、证据、风险和门禁均通过租户关联查询，不能先按 ID 获取后再补权限判断。

同一请求内需要多个领域数据时使用同一个数据库会话批量查询；禁止为每个卡片单独查询。列表页面使用聚合计数或预加载，避免 N+1。

### 4.3 页面域映射

84 页按以下数据域分片，每一页仍在注册表中单独声明：

| 页面 | 数据提供器 |
| --- | --- |
| S01-S03 | 会话、租户成员、隐私授权 |
| S04-S09 | 演出、案例、机会、搜索结果 |
| S10-S18 | 项目、版本、创建上下文、服务端草稿摘要 |
| S19-S24 | 艺人、城市、档期、场馆候选 |
| S25-S33 | 项目输入、财务版本、保本线、敏感性、资金缺口 |
| S34-S42 | 判断、假设、事实、证据、解析任务、资料缺口与冲突 |
| S43-S51 | 风险、门禁、决策、版本差异、报告和分享记录 |
| S52-S60 | Agent 分析任务、业务任务、阻塞、变化提醒和授权 |
| S61-S66 | 巡演、站点、售票快照、实际结算和复盘 |
| S67-S72 | 用户、成员、角色、通知、设置、授权和邀请 |
| S73-S81 | 由真实上下文和错误状态驱动的通用状态页 |
| S82-S84 | 服务连接、通知偏好、个人信息与授权记录 |

S01、S03、S13-S17、S41、S46、S47、S51、S53、S54、S57、S60、S65、S66、S70-S72、S79、S80、S82-S84 的提交动作继续调用领域写接口。聚合接口只负责加载提交前后的页面状态。

## 5. 数据模型补充

仅在现有领域模型无法表达真实数据时补表，不建立通用 CMS 页面表。

- `venues`: 场馆名称、城市、容量、报价、消防与交通状态。
- `tour_plans`、`tour_stops`: 巡演及站点顺序、档期、关联项目和执行状态。
- `notifications`: 用户可见消息、类型、关联实体、已读状态。
- `project_actuals`: 实际收入、实际成本、售票人数、结算状态和确认人。
- `ticketing_snapshots`: 项目售票时间点、售出票数、收入和来源。
- `user_settings`: 通知偏好、草稿策略和个人设置。
- `privacy_consents`: 授权类型、范围、状态和授权时间。
- `member_invitations`: 租户邀请、角色、过期时间和状态。
- `agent_permissions`: Agent 可执行动作范围及高风险动作限制。
- `project_drafts`: 用户、租户、创建步骤和草稿内容，用于跨设备恢复。

新增表必须具备租户或可追溯到租户的外键。初始化数据只可写入可说明来源的领域记录，并使用业务唯一键幂等去重；不得初始化示例利润、虚构消息或伪造实际结果。

数据库结构同时更新 SQLAlchemy 模型和 `app/schema.sql`。测试环境继续使用内存 SQLite，生产配置保持 MySQL。

## 6. 前端架构

### 6.1 数据加载

`src/services/api.ts` 新增 `getMiniappScreen(screenId, context)`。`BlueprintScreen` 不再维护按 screen ID 调用多个领域读取接口的 `switch`，统一执行一次页面聚合请求。

页面状态收敛为：

- `loading`: 首次加载或刷新。
- `success`: 成功且有数据。
- `empty`: 成功但无数据，展示服务端 `empty_state`。
- `error`: 请求失败，展示错误信息和重试。

删除 `example` 状态、`getFixtureItems` 引用和 `src/data/fixtures.ts`。页面切换时先清空上一页数据，避免错误时残留旧内容。

`screenDefinitions` 只保留稳定的页面元信息和导航声明。所有会随业务变化的标题、关键数字、状态和列表内容使用聚合响应。

### 6.2 搜索选择

统一搜索选择组件支持：

- 300ms 防抖。
- 输入值归一化后的模糊匹配。
- 加载、无结果和错误状态。
- 分组结果与键盘/触摸选择。
- 点击后同时保存 `entity_type`、真实 `entity_id` 和显示文本。
- 项目、艺人、场馆、城市和成员等实体使用同一交互契约。

服务端通过聚合接口的 `options.search` 声明搜索能力和查询目标；实际候选查询可继续使用既有领域搜索接口，缺少时再补领域只读接口。组件不得从页面静态数组生成业务候选。

### 6.3 原生构建产物

Taro 源码是行为源。`dist` 仅由现有构建/生成流程产生，不在源代码和原生 runtime 之间维护两套独立业务逻辑。现有生成脚本需同步改为消费聚合契约，并增加产物一致性测试。

## 7. 空状态与失败处理

- 空状态必须来自成功查询后的空结果，不能用网络失败代替。
- 项目上下文缺失时，项目级页面进入 S76 或返回 `422` 对应提示，不再使用项目 ID `1`。
- 401 跳转 S81，403 跳转 S77，409 跳转 S78。
- 普通网络错误保留当前路由和输入草稿，显示重试入口。
- 提交类操作失败后重新查询领域实体状态，再决定是否重试，避免重复写入。
- 金融数据不完整时展示缺失字段清单，不渲染利润、保本线或敏感性数字。

## 8. 测试策略

### 8.1 后端

- 契约测试：合法 screen、非法 screen、统一字段、错误码和 Pydantic 序列化。
- 映射测试：S01-S84 均注册且没有默认提供器。
- 权限测试：跨租户项目、版本、任务和证据不可读取。
- 聚合测试：数量、状态、金额和空状态均由数据库记录计算。
- 查询测试：关键列表不产生按条目增长的查询次数。
- 模型测试：新增表结构、外键、幂等初始化和实际结果不可伪造。

### 8.2 小程序

- API 测试：统一解析 `{"code": 0, "data": ...}`，并传递完整上下文。
- 状态测试：loading、success、empty、401、403、409、422、网络错误和重试。
- 映射测试：84 页均声明聚合数据映射与写操作映射。
- 静态防回退测试：源码和生成产物不引用 `fixtures`、示例利润或 `example` 状态。
- 搜索组件测试：防抖、模糊结果、点击选中、真实 ID 持久化、空结果和失败。
- 流程测试：项目创建、财务测算、证据核验、门禁确认、决策、任务批处理、实际结果与设置保存。

每个切片先增加会失败的测试，确认失败原因后实现最小代码，再执行后端、前端和原生产物回归测试。

## 9. 分片实施顺序

1. **基础契约**：增加 Pydantic 响应模型、`SCREEN_PROVIDERS` 完整注册、聚合路由、前端 API 类型和 84 页映射测试。
2. **项目主链路**：S10-S18、S25-S51，覆盖项目、财务、依据、风险、门禁、决策和报告。
3. **任务与 Agent**：S52-S60，复用当前任务批处理和分析任务数据。
4. **发现与组合**：S04-S09、S19-S24，补齐场馆等领域数据和统一搜索选择。
5. **巡演与复盘**：S61-S66，补齐巡演、票务快照和实际结果。
6. **账户协作**：S01-S03、S67-S72、S82-S84，补齐通知、设置、隐私和邀请。
7. **状态页与清理**：S73-S81，删除 fixtures 和所有示例回退，统一错误路由。
8. **全量验收**：生成 `dist`，执行后端测试、小程序测试、构建检查及 S01-S84 数据/API 映射检查。

每个切片只有在其页面不再读取静态业务数据、读写流程测试通过且没有跨租户泄漏时才算完成。

## 10. 非目标

- 不把现有领域写接口合并进聚合接口。
- 不建立可任意配置页面内容的通用 CMS 表。
- 不在本次改造中重做 84 页视觉设计。
- 不用前端计算替代后端财务结果。
- 不为缺失业务数据制造看似真实的默认记录。

## 11. 验收标准

- `GET /miniapp/screens/{screen_id}` 覆盖 S01-S84，并返回统一契约。
- 84 页的动态金额、状态、数量、列表和选项均可追溯到数据库或确定性计算。
- 小程序源码和原生构建产物中不存在 `fixtures.ts` 依赖、示例业务回退和默认项目 ID。
- 所有搜索选择字段支持模糊下拉、点击选中并保存真实 ID。
- 原有领域写操作保持兼容并通过回归测试。
- 新增模型、聚合函数、组件和映射均有单元测试。
- 后端测试、小程序测试、类型检查和微信构建全部通过。
