# 小程序数据库候选项与模糊选择设计

## 1. 目标

为小程序项目创建流程补充真实数据库候选项，解决 S14“地点与时间”等页面只有空输入框、用户无法快速选择已有业务数据的问题。

交互必须同时支持：

1. 输入框未输入时，展示高频或近期使用的候选项，用户可直接点选。
2. 输入关键词后，对候选数据进行模糊匹配并展示列表。
3. 点击列表项后回填项目草稿；关联实体必须同时保存真实业务 ID。
4. 保留手动输入能力。数据库无候选数据时隐藏候选区域，不使用示例或模拟数据。

## 2. 范围

本次覆盖项目创建流程 S13-S16：

| 页面 | 字段 | 数据来源 |
| --- | --- | --- |
| S13 基本信息 | 历史项目、艺人、项目类型 | 当前租户 `Project`、全局 `Artist` |
| S14 地点与时间 | 城市、场馆、档期 | 当前租户 `Project`、`Venue`、`TourPlan/TourStop`，公开 `Show` |
| S15 规模与资金 | 可售规模、可用资金、平均票价 | 当前租户历史 `Project`，场馆容量仅用于规模候选 |
| S16 成本信息 | 艺人、场馆、宣发、制作成本 | 当前租户历史 `Project` |

S17 继续负责复核，不新增候选控件。S19、S22、S23、S24 等已有独立候选列表的页面继续使用现有聚合数据，但统一遵守本规格的真实数据、可点击、实体 ID 和空状态约束。

## 3. 方案

采用方案 A：候选项由现有页面聚合接口返回。

`GET /miniapp/screens/{screen_id}` 在 S13-S16 的 `options` 中增加 `candidate_groups`。页面首屏无需额外请求即可展示高频候选；文本输入后的远程模糊查询继续复用并扩展 `GET /miniapp/search`。

不新增独立推荐接口。候选项属于页面读取模型，放入现有聚合接口可保持租户、用户和页面上下文校验一致。

## 4. 响应契约

`options.candidate_groups` 为列表，每组结构如下：

```json
{
  "key": "venues",
  "label": "高频场馆",
  "field": "venue",
  "search_mode": "remote",
  "items": [
    {
      "key": "venue-12",
      "label": "南京奥体中心",
      "description": "南京 · 容量 13000",
      "entity_type": "venue",
      "entity_id": 12,
      "patch": {
        "venue_id": 12,
        "venue": "南京奥体中心",
        "city": "南京",
        "venue_capacity": 13000
      }
    }
  ]
}
```

约束：

- `key` 在同组内稳定且唯一。
- `label` 和 `description` 只用于展示。
- `patch` 是点选后原子写入项目草稿的字段集合。
- 实体候选必须携带 `entity_type`、`entity_id`。
- 数值候选不伪造实体 ID，`patch` 仅包含对应数值字段。
- API 继续使用 `{"code": 0, "data": {...}}` 包装结构。

## 5. 数据生成规则

### 5.1 租户和权限

- `Project`、`Venue`、`TourPlan/TourStop` 只读取当前租户数据。
- `Artist` 和公开 `Show` 可作为公共候选来源。
- 不返回其他租户的项目名、场馆、成本、资金或档期信息。

### 5.2 高频排序

- 先按当前租户历史项目中的使用次数降序。
- 次序相同时按最近使用时间或记录 ID 降序。
- 公共候选在租户候选之后，艺人可用 `heat_score` 作为次级排序。
- 每组默认最多返回 8 项，去除空值、零值和重复值。
- 数值去重按实际数值处理，展示时增加千分位和单位。

### 5.3 数据边界

- 项目类型来自当前租户已保存的 `Project.type`，不返回未使用的静态示例。
- 城市从当前租户项目、场馆、巡演站点及公开演出中合并去重。
- 场馆优先使用当前租户 `Venue`，并保留 `venue_id`。
- 档期来自历史项目计划时间、巡演站点时间和公开演出日期。
- 规模、资金、票价和成本只使用数据库中大于零的真实数值。
- `Venue.quote` 为非结构化文本时不得直接写入场馆成本；成本候选以历史项目结构化字段为准。

## 6. 搜索与点选交互

### 6.1 首屏高频候选

- 每个支持候选的输入框下方展示对应高频项。
- 候选采用紧凑列表或标签组，不嵌套卡片。
- 点击候选后执行其 `patch`，立即更新页面值和本地项目草稿。

### 6.2 模糊搜索

- 城市、场馆、艺人、历史项目输入后使用 300ms 防抖调用 `/miniapp/search`。
- 匹配名称、城市、标签和其他已有可搜索文本字段。
- 搜索结果按实体类型分组，列表项必须可点击。
- 数值字段在已下发的数据库候选中本地过滤；用户仍可直接输入任意合法数值。

### 6.3 联动回填

- 选择场馆：回填 `venue_id`、`venue`、`city`、`venue_capacity`。
- 选择历史项目：回填允许复用的基础字段和 `source_project_id`，不覆盖用户已经修改且本次候选未提供的字段。
- 选择艺人：回填 `artist_id`、`artist_name`。
- 选择其他候选：只更新 `patch` 中声明的字段。

## 7. 前端实现

### 7.1 Taro

- 扩展现有 `SearchSelect`，支持初始候选、输入过滤、远程搜索、加载态和真实空状态。
- `BlueprintScreen` 根据 `candidate_groups` 渲染 S13-S16，不在组件中硬编码候选值。
- 点选后统一通过草稿更新函数持久化到 `STORAGE_KEYS.projectDraft`。

### 7.2 原生微信产物

- `generate-wechat-dist.mjs` 生成与 Taro 一致的候选列表、搜索状态和点击回填逻辑。
- S14 不再退化为单个通用输入框。
- 生成后的 `dist` 必须包含真实候选首屏展示和模糊搜索交互。

## 8. 空状态与错误处理

- 候选为空：隐藏高频候选列表，保留输入框。
- 搜索无结果：显示“未找到匹配数据”，不显示固定示例。
- 搜索失败：保留当前输入和已有候选，显示可重试提示。
- 候选关联实体已删除：忽略该项并重新加载，不写入无效 ID。
- 草稿恢复后，已选值继续展示；候选数据只提供选择，不覆盖草稿。

## 9. 测试

### 后端

- S13-S16 返回数据库生成的 `candidate_groups`。
- 验证高频排序、去重、数量上限和空值过滤。
- 验证租户隔离，其他租户项目和场馆不得出现在候选中。
- 验证场馆候选携带真实 `venue_id` 和联动 `patch`。
- 验证无数据时返回空候选，不回退到模拟值。

### Taro

- 首屏显示高频候选。
- 输入关键词后展示模糊匹配列表。
- 点击城市、场馆、艺人和数值候选后正确更新草稿。
- 搜索失败和无结果状态可见，手动输入不受影响。

### 原生微信

- 生成产物覆盖 S13-S16 候选展示、搜索和点选。
- 校验所有实体候选绑定真实业务 ID。
- 保留现有 84 页面注册、统一详情页和创建流程测试。

## 10. 验收标准

1. S14 打开后可直接看到数据库中的高频城市、场馆和档期。
2. 输入关键词可模糊搜索，结果列表可点击。
3. S13-S16 的同类字段均具备数据库候选。
4. 点选场馆等关联项后，展示值与实体 ID 同步保存。
5. 不产生跨租户数据泄露，不出现模拟候选。
6. Taro 与原生微信行为一致，新增内容均有单元测试。
